# TASK-20260831-003 Survey v5 表示文言・回答体験仕様

> 状態: 2026-09-07 operator実機レビューを反映した実装正本
> 対象: 新しいschema v5・新しいSTG slug
> 非対象: 回答済みschema v4／`playnavi-voice-2026-stg-review-v2`の意味変更

## 1. 用語と変更境界

```text
Survey v5
├─ 回答本体: 選択回答、自由記述、表示順。UIDを含まない
├─ 報酬判定: ログイン情報を称号付与の判定にだけ使う
├─ 通常選択肢: 質問が測るカテゴリに属する回答
├─ 補助選択肢: その他、該当なし、判断不能、回答辞退
├─ 機能別補足: 「役立っている機能」で選んだ機能ごとの任意記述
├─ 質問別補足: 各選択質問に付ける任意記述
└─ 理由振り分け: あまり使っていない機能を理由別に分類する操作
```

- schema v4はすでにSTGで回答を受け付けている。タイトル、期間、設問の意味、選択上限、回答形を同じslugで変更しない。
- v5は新しいschema versionと新しいSTG slugで作成し、v4の回答・集計・下書きから隔離する。
- 本書の表示順は、導入、P1〜P13、確認、送信とする。分岐により表示されないページは進捗の分母へ含めない。
- 本書の文章をデータベース用IDへ変換してはならない。保存値は別途定義する安定IDを使う。

## 2. 共通表示

### 2.1 タイトル

    ユーザーアンケート 2026.09

タイトルは途中改行、末尾省略、横方向の縮小変形をしない。

- `white-space: nowrap`
- `font-size: min(32px, 6.2vw)`
- `letter-spacing: 0`
- 320px幅でも左右のpadding内へ収める
- ブラウザ文字拡大時もviewport幅に連動させ、クリップや横スクロールを発生させない

### 2.2 タイトル下の装飾線

48px固定の短い線を廃止する。

- 幅: `min(76%, 340px)`
- 高さ: 3px
- タイトルとの間隔: 14px
- 角丸: 999px
- 現行のprimary系グラデーションを維持する

### 2.3 説明

    PlayNaviの改善に向けて、普段のゲームとの関わり方や、
    ご利用中に感じていることをお聞かせください。

タイトルは1行固定だが、説明は読みやすい位置で折り返してよい。

### 2.4 ログイン方法の選択画面

見出し:

    回答方法を選択してください

案内:

- アカウントで回答すると、回答完了後に報酬（称号）を受け取れます。
- ログイン情報は報酬付与の判定にのみ利用し、回答内容には紐づけません。
- ログインせずに回答することもできますが、ゲスト回答では報酬を受け取れません。

ボタン:

- `Appleでサインイン`
- `Google でログイン`
- `報酬なしでログインせず回答する`

### 2.5 アカウント回答者の「ご回答の前に」

下記3項目だけを表示する。現行の端末保存、セグメント集計、候補数等の追加箇条書きは表示しない。

- 匿名形式のアンケートです。（ログイン情報は、報酬付与の判定にのみ利用します）
- 回答内容にかかわらず、回答を送信すると報酬（称号）を受け取れます。
- 報酬は、アンケート回答終了後、数日以内に配布します。

### 2.6 ゲスト回答者の「ご回答の前に」

ゲストへ報酬を受け取れると誤認させないため、アカウント回答者とは文言を分ける。

- 匿名形式のアンケートです。（PlayNaviのログイン情報は使用しません）
- ゲスト回答では、報酬（称号）を受け取れません。
- 設問と回答内容の扱いは、アカウントで回答する場合と同じです。

### 2.7 共通の任意入力

自由記述そのものを回答するP3を除き、すべての選択質問に任意の補足欄を置く。

開閉ラベル:

    回答について補足する（任意）

入力欄ラベル:

    補足したいことがあれば入力してください。

仕様:

- 初期状態は閉じる。開かなくても質問は完了できる。
- 入力上限は400文字。残り文字数ではなく `入力文字数 / 400文字` を表示する。
- placeholderだけをラベルの代わりにしない。
- 任意欄を空にしても必須エラーを出さない。
- 分岐変更で質問が非表示になった場合、その質問の補足は送信対象から除外する。
- 選択回答のタップ後も、補足欄を開いて入力できる導線を失わせない。
- 「短いひとことで大丈夫です」「ひとことでも」等、短文を繰り返し要求する文言は使わない。

2. ほかのサービスや方法で足りている
3. 使う機会がない
4. 使い方がわからない
5. 使いにくい
6. このアンケートで初めて知った

## 19. 質問カードの構造と見た目

添付`IMG_3252.png`で確認した、質問文がfieldset枠線へ食い込む表示を廃止する。

推奨DOM:

```html
<section class="question-card" data-error-id="...">
  <h3 id="question-..." class="question-heading">
    <span>質問文</span><span class="required-badge">必須</span>
  </h3>
  <fieldset class="question" aria-labelledby="question-...">
    <legend class="sr-only">質問文</legend>
    <!-- 選択肢 -->
  </fieldset>
</section>
```

- 外枠は`section.question-card`へ付ける。
- `fieldset`はborderなしとし、native legendによる枠線の欠けを発生させない。
- 表示質問文と必須badgeはカード上端から16〜18px内側に置く。
- 必須badgeは小さなpill表示にし、質問文へ文字列として不自然に連結しない。
- question headingは左揃え、16〜18px、line-height 1.55。長文は自然に折り返す。
- page headingと質問文が同じ意味を重複する場合も、page headingは領域名、question headingは回答を求める完全な文にする。
- validation error時はカード全体のborderとメッセージを関連付け、色だけで示さない。

## 20. 理由振り分けUI

### 20.1 共通状態

- 画面上部へ`未分類 n件`を表示する。
- 選んだ機能をチップまたはカードとして未分類トレイへ置く。
- 理由は8つのbucketとして表示し、各bucketに件数を表示する。
- 操作後に`元に戻す`を提供する。
- 未分類が0件になるまで次へ進めない。エラー時は最初の未分類項目へ移動する。

### 20.2 ポインターによるドラッグ&ドロップ

- デスクトップでは、機能チップのdrag handleから理由bucketへ移動できる。
- iOS WebViewを含むタッチ環境でもpointer eventsを使って提供できる場合は、長押し後のドラッグを許可する。
- ページスクロールとの競合を避ける。チップ全体を常時drag handleにしない。
- ドラッグ開始、移動可能先、ドロップ完了、キャンセルを視覚的に示す。
- 画面端の自動スクロールは低速にし、`prefers-reduced-motion`では無効化する。

### 20.3 モバイルの同等操作

ドラッグだけを唯一の回答方法にしない。

1. 機能チップをタップする。
2. bottom sheetで8理由を表示する。
3. 理由をタップすると、そのbucketへ移動する。
4. 割り当て済みチップの`振り分け先を変更`から再選択できる。

このタップ操作をiOS／Androidの主な代替操作とし、ドラッグに失敗しても回答を完了できるようにする。

### 20.4 キーボードと読み上げ

- 各チップはTabで到達可能にする。
- SpaceまたはEnterでチップを選択し、理由一覧を開く。
- 矢印キーで理由を移動し、SpaceまたはEnterで確定できる。
- Escapeでキャンセルする。
- `aria-describedby`で現在の理由と操作方法を伝える。
- `aria-live="polite"`で「プレイログを『使いにくい』へ移動しました」のように結果を読み上げる。
- 視覚順とDOM順を一致させる。CSS orderだけで並べ替えない。

## 21. 直近1ヶ月間の内部定義

画面表示はすべて`直近1ヶ月間`に統一する。`4週間`、`直近30日間`、具体的な開始・終了日の注釈を混在させない。

内部の再現可能な集計期間:

- timezone: `Asia/Tokyo`
- end: 初回下書き作成日の前日
- days: 30日間
- start: endを含めて30日前ではなく、30日間となる開始日
- 下書き再開時もendを変えない

`rolling_calendar_month`という名称は、前暦月か過去1ヶ月か曖昧になるため使わない。物理契約では`reference_period_days = 30`、`reference_period_end_offset_days = 1`等、意味が一意な値を使う。

## 22. 質問別補足の論理対応

`answer_notes`は次の17キーだけを持つ。Backend契約の安定IDを正とし、表示文言からキーを生成しない。

| キー | 対応する表示質問 |
|---|---|
| `play_frequency_1m` | P1-Q1 ゲームを遊ぶ頻度 |
| `primary_play_device_1m` | P1-Q2 主に使った機器 |
| `usage_1m` | P2-Q1 PlayNavi利用日数 |
| `overall_satisfaction` | P2-Q2 PlayNavi全体的満足度 |
| `info_seek_days_1m` | P4-Q1 ゲーム情報を見る頻度 |
| `recording_preference` | P4-Q2 残したい記録の詳しさ |
| `valuable_features` | P5 役立っている機能の選択全体 |
| `unused_features` | P6の機能選択とP7の理由振り分けに対する共通補足 |
| `primary_problem` | P8 現在利用者の改善項目 |
| `dormant_reason` | P8 休眠者の利用しなかった理由 |
| `problem_outcome` | P9 困りごとがあったときの行動 |
| `future_role` | P10 これから期待する役割 |
| `future_candidates` | P11 追加・強化してほしい機能 |
| `future_priority` | P12 最も期待する機能 |
| `future_detail_a` | P12 最優先候補の詳細質問a |
| `future_detail_b` | P12 最優先候補の詳細質問b |
| `improvement_vs_candidate` | P13 改善と新機能の比較 |

- P3は回答本体が自由記述であり、質問別補足を重ねない。
- P5の機能別補足は`answer_notes.valuable_features`とは別に保持する。
- P6とP7は`answer_notes.unused_features`を共有する。画面上はP7末尾に表示し、理由振り分けをしない排他回答ではP6末尾に表示する。
- P8の`primary_problem`と`dormant_reason`は別キーとし、表示されない側を空文字にする。
- そのほかの分岐非表示キーも空文字にする。未知キー、`null`、400文字超過を受け付けない。

## 23. 回答操作

- 単一選択は選択直後に状態を保存する。
- 同じページに次の必須質問がある場合、pointer操作時だけ既存の次問自動スクロールを使える。ただし質問別補足を開く操作を妨げない。
- ページそのものを予告なく自動遷移しない。
- キーボード、VoiceOver、TalkBack操作時は自動フォーカス移動を行わない。
- 複数選択は選択後に`次へ`を押す。タップ順を順位と解釈しない。
- P5で機能を選ぶと機能別補足をその場に表示するが、自動フォーカスはしない。
- 戻る、選択解除、分岐変更後も、送信対象と表示中の回答を一致させる。

## 24. 曖昧点に対する確定判断

| operator指摘 | 本仕様の判断 |
|---|---|
| 「すべての欄」に任意自由入力 | 自由記述本体を除く17論理質問に質問別補足を置く。全選択肢1件ごとには置かない。P5だけは明示要件に従い選択機能ごとにも置く |
| 役立つ機能の最大3件撤廃 | 通常26機能をすべて選択可能にする |
| あまり使っていない機能 | 独立ページの必須複数選択にし、通常26機能をすべて選択可能にする |
| 理由をDnDで配布 | 通常機能全件を1理由へ割り当てる。DnDとタップ／キーボード操作を同等に提供する |
| P5とP6で同じ機能を選択 | 「低頻度だが必要なときに役立つ」を保持するため許可する |
| 直近1ヶ月間 | 画面では同表記へ統一し、内部ではJST前日を終端とするrolling 30 daysに固定する |
| 「特にない」「判断できない」がカテゴリに見える | 通常群からdivider、間隔、neutral背景、小見出しで分離し、末尾固定にする |
| Q1を頻度へ変更 | 時間帯IDを再利用せず、新しい頻度IDを持つv5にする |
| タイトル・設問変更 | 回答済みv4へ上書きせず、新schema／新slugへ分離する |
| 報酬案内 | アカウント回答とゲスト回答で文言を分け、ゲストへ称号付与を誤認させない |

## 25. 実装受け入れ条件

- タイトルが320px、390px、412px、PC幅で1行表示される。
- タイトル下の装飾線が48px固定でなく、タイトルとの視覚的なまとまりを作る。
- 質問文と必須badgeがカード枠内にあり、枠線がlegendで途切れない。
- P1の時間質問が頻度質問へ変わり、P1-Q1／Q2直下に旧説明文がない。
- 期間表記がすべて`直近1ヶ月間`で、`4週間`と`直近30日間`が残らない。
- `候補を見る前に`と`短いひとことで大丈夫です`が残らない。
- P5は最大3件制限がなく、選択機能直下の任意入力を持つ。
- P6は独立必須ページ、P7は選択全機能の理由割り当て必須ページである。
- P7をdrag、タップ、キーボードの各経路で完了できる。
- 17論理質問の質問別補足が任意で利用でき、未入力でも高速に完了できる。

## 27. 2026-09-08 feedback revision (schema v6)

回答済みのschema v5は変更せず、同じ質問定義と29キー回答形式を再利用する
schema v6／新slugへ、次の表示変更だけを分離する。

- P5は、第1セクションで機能を選び、第2セクションに選択済み各機能の任意理由欄をまとめる。
- P6/P7は同じページに統合し、選択済み各機能に理由ラジオを1組ずつ表示する。DnDと理由専用ページは廃止する。
- 表示中の`answer_notes`は折り畳まず、最初から入力欄を表示する。
- P9はP3ではなくP8の追質問なので、P8の第2セクションへ統合する。P3は指定された任意自由記述のまま独立させる。
- P3質問は`日頃ゲームを楽しむなかで、「こういうことがしたいのにできない」と感じることがあれば教えてください。（任意）`、説明は`PlayNaviとは関係ないことでかまいません。思いつかなければ、空欄のまま次へ進めてください。`とし、説明を入力欄より前に置く。
- 完了画面は上段`回答受け付けました`、中央`ご回答いただきありがとうございました`、本文`このまま画面を閉じて構いません。報酬のご提供まで今しばらくお待ちください。`とし、称号表示欄を出さない。
- 報酬ありの認証回答は、回答本文とUIDを結合せず、別の報酬台帳で同一survey／UIDの2回目を拒否する。ゲストは人物を識別できないため、厳密な1人1回の保証対象外とする。

受入条件は、schema v1〜v5の全回帰、schema v6の実Chrome完走、DnD非表示、
機能別理由の保存、29キー完全一致、完了文言完全一致、回答済み再訪時のフォーム非表示、
および同一UIDの同時送信で回答1件・報酬台帳1件である。

## 28. 2026-09-08 final free-text revision (schema v7)

回答済みのschema v1〜v6と保存済み回答は変更しない。schema v7は新slugで作成し、
schema v6の表示と回答契約から次の2点だけを変更する。

- `primary_problem`の条件付き追質問だった「困りごとがあったときの行動」
  (`problem_outcome`)を質問、回答キー、`answer_notes`キーから完全に除く。
- レビュー画面の直前に任意自由記述
  `最後に、ここまでに書けていないことで言いたいことや伝えたいことがあればご自由にお書きください。`
  (`final_comment`)を追加する。上限はUnicodeコードポイントで2000文字とする。

schema v7の公開定義には`problem_outcome_options`を含めず、代わりに
`final_comment_max_length: 2000`を含める。Web、プロキシ、Edge、DBは未知キー、
欠落キー、2001コードポイントを拒否し、2000コードポイントは受理する。
同じアンケートの改訂slugは共通の`response_group_id`を持つため、schema v6以前に
認証回答済みのUIDへv7を再回答させない。別アンケートへの回答は妨げない。

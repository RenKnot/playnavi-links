## 1. 用語と状態の定義

    アンケート
    ├─ 調査設計: 誰に、何を、何のために聞くか
    ├─ 回答体験: 少ない負担で、誤りを直しながら回答できる画面
    ├─ 回答本体: 設問への回答。UIDを含まず、UIDと結合しない
    ├─ 報酬処理: UIDを称号付与にだけ使う独立保存領域
    └─ 集計: 個人を識別せず、定義済みの母数で回答を解釈する処理

    回答者
    ├─ アカウント回答者: ログインし、回答完了時に称号を受け取れる人
    └─ ゲスト回答者: ログインせず、称号を受け取らない人

    利用状況
    ├─ 現在利用: 直近30日間に1日以上利用
    ├─ 休眠: 以前は利用したが、直近30日間は利用していない
    ├─ 未利用: 一度も利用していない
    └─ 不明: 利用状況を覚えていない

    将来候補の選択
    ├─ 候補選択: 順位を付けず最大3件を選ぶ
    ├─ 最優先: 選択候補の中から1件だけ明示する
    └─ 詳細化: 最優先候補についてだけ最大2問に答える

    実装状態
    ├─ schema v2: 現行コードとSTGに存在する旧回答契約
    ├─ schema v3: Web・Supabaseコード実装とローカル検証が完了した新回答契約。STG適用前
    ├─ 承認済み実装仕様: operator承認を受け、コードとSTG検証へ進む仕様
    └─ 公開版: 承認、STG E2E、production gateを通過して凍結した仕様

本書でいう匿名回答とは、回答本体をUID、メールアドレス、OAuth識別子その他のアカウント識別子に紐づけて保存・集計しないことを指す。「完全匿名」や「追跡不能」とは表現しない。回答行には回答者区分と日単位の送信日が残り、通信基盤には標準的なセキュリティログが存在し得るためである。

## 2. 調査目的

### 2.1 主目的

現状の利用継続を支える価値と阻害する問題を把握し、今後提供する価値・追加機能の優先候補を絞る。

### 2.2 副目的

- 既存26機能の中で特に守るべきものを把握する。
- 利用しない理由を、不要、代替手段、機会不足、認知不足、使いにくさに分ける。
- 動作、不具合、導線、情報不足など、個別機能に閉じない問題を把握する。
- メディア、ゲームDB、記録、投稿、クリエイター、コミュニティ、PC、AIの構想を利用者の体験に翻訳して検証する。
- 最優先候補の具体的な仕様と利用条件を絞る。
- 作り手が提示した候補にない期待や不便を、候補提示前の任意記述で発見する。

### 2.3 この調査だけでは断定しないこと

- 全利用者、未獲得ユーザー、ゲームユーザー全体の支持率。
- 全26機能の利用率、認知率、満足度。
- 非選択機能が不要であること、または削除してよいこと。
- 希望回答が実際の継続利用へつながること。
- 一般利用者の期待から、クリエイターの参加意思や事業採算を推定すること。
- 票数だけから、実装費、依存関係、権利条件を無視して開発順を決めること。
- 自発回答へ無作為標本と同じ標本誤差を付けること。

## 3. 対象者と回答導線

### 3.1 対象者

- 主対象: PlayNaviを現在利用している、または以前利用した人。
- 補助対象: 共通Web URLへ到達した未利用者とゲスト回答者。
- 認証方式と利用経験は別軸とし、ゲストを未利用者とみなさない。
- 年齢、地域、OSによる制限は現時点で設けない。

### 3.2 導線

    PlayNavi 4.2.2以降のお知らせ
    └─ アプリのログイン状態を一回限りでWebへ引き継ぐ
       └─ Webで再ログインせず回答開始

    PlayNavi 4.2.1以前のお知らせ、公式Web、SNSの共通URL
    ├─ GoogleまたはAppleでログイン
    │  └─ アカウント回答。完了時に称号付与
    └─ 報酬なしでログインせず回答
       └─ ゲスト回答。称号なし

入口や認証方式によって質問内容や候補順の母集団を変えない。回答本体には認証情報、UID、募集経路を保存しない。アカウント／ゲストの区分はサーバーが回答行の `respondent_kind` に記録するが、UIDとは結合しない。募集経路は信頼できる取得経路が未実装のため、schema v3では保存・集計しない。

### 3.3 冒頭表示

画面タイトル、アンケート説明、固有ガイドはキャンペーン設定から表示し、固定文言にしない。

画面タイトル:

    PlayNavi Voice 2026

冒頭説明:

    PlayNaviで役立っていること、困っていること、これから期待することを教えてください。
    選択式が中心で、文章の入力は任意です。率直なご意見を今後の改善に活かします。

共通ガイド:

    ・回答内容はUIDに紐づけず、匿名で保存・集計します。
    ・UIDは、回答完了の称号を付与するためだけに使用します。
    ・回答内容は他のユーザーには公開しません。
    ・文章の入力はすべて任意です。空欄でも回答完了と称号の受け取りに影響しません。
    ・評価内容や機能への賛否によって、称号の受け取り条件は変わりません。
    ・送信後は、UIDから自分の回答を特定して変更・削除することはできません。

ログイン選択画面:

    ・アカウントに紐づく報酬をご提供するため、ログインをお願いします。
    ・UIDは称号の付与だけに使用し、回答内容には紐づけません。
    ・ログインせずゲストとして回答することもできますが、ゲスト回答では称号を受け取れません。

所要時間はschema v3の最終UIで実測するまで表示しない。

## 5. schema v3回答契約

### 5.1 版と識別子

- schema_version: 3
- questions.kind: playnavi_voice_2026_reviewed
- production slug候補: playnavi-voice-2026
- 新STG slug: playnavi-voice-2026-stg-review-v1
- 意味を変える再改訂時: playnavi-voice-2026-stg-review-v2 以降
- schema v2のslug、定義、回答を上書きしない。

### 5.2 回答キー

| キー | 型・上限 | 内容 |
|---|---|---|
| usage_30d | 列挙・必須 | Q1 |
| overall_satisfaction | 列挙または空文字 | Q2。未利用者は空文字 |
| unprompted_need | 0〜400文字 | Q3。未回答は空文字 |
| valuable_features | 利用経験者は1〜3件、未利用者は空配列 | Q4。26機能IDまたは排他値none／unknown |
| unused_feature | 機能IDまたは空文字 | Q5-a |
| unused_reason | 列挙または空文字 | Q5-b。Q5-a未選択時は空文字 |
| primary_problem | 列挙または空文字 | Q6。休眠・未利用は空文字 |
| dormant_reason | 列挙または空文字 | Q6-L。休眠者だけ値を持つ |
| problem_comment | 0〜300文字 | Q6任意記述。具体的問題がない場合は空文字 |
| problem_outcome | 列挙または空文字 | Q7 |
| future_role | 列挙・必須 | Q8 |
| future_role_other | 0〜400文字 | Q8その他の任意記述。他の選択時は空文字 |
| future_candidates | 1〜3件の重複なし配列 | Q9。12候補ID、other、排他値none／unknown |
| future_other | 0〜400文字 | Q9その他の任意記述。他の選択時は空文字 |
| future_priority | 12候補ID、other、空文字 | Q10または1件選択から引継ぎ |
| future_priority_mode | inherited、explicit、空文字 | 1件引継ぎか複数候補からの明示選択か |
| future_detail_a | 列挙または空文字 | Q11-a。回答は任意 |
| future_detail_b | 列挙または空文字 | Q11-b。回答は任意 |
| future_detail_other | 0〜400文字 | other最優先時の任意記述 |
| improvement_vs_candidate | improvement、candidate、tie、空文字 | Q12 |
| feature_display_order | 26機能IDの重複なし配列 | Q4の実表示順。全26件を1回ずつ含む |
| future_display_order | 12候補IDの重複なし配列 | Q9の実表示順。全12件を1回ずつ含む |

回答本体は上記22キーだけを持ち、欠けたキー、未知キー、`null`を受け付けない。非該当・任意未回答は空文字または空配列で表し、「判断できない」は定義済みの列挙値で表す。

`schema_version`とslugは回答本体ではなく、受付対象の`surveys`行とURL／送信経路で確定する。`respondent_kind`はサーバーが回答行へ設定する。通信再試行用の`submission_token`はPOST bodyの回答本体の外側で受け取り、ハッシュだけを保存する。これらを22キーへ混入させない。

回答payload、回答保存領域、下書き、集計用データにはUID、メールアドレス、OAuth識別子、access token、ID token、refresh tokenを含めない。ブラウザ下書きは22キーと送信用tokenを別フィールドで保持し、送信用tokenを回答内容として送らない。

### 5.3 共通検証

- 列挙値以外を拒否し、未知キーを受け付けない。
- テキストはUTF-8で検証し、各上限と回答全体64KiB上限を適用する。
- 配列は重複、上限超過、未知IDを拒否する。
- none、unknownは通常候補と併用できない。
- 表示されない分岐の値は空文字または空配列とし、古い回答を送信対象から除外する。
- 空値と「判断できない」を兼用しない。判断できないは`unknown`等の列挙値として保存する。
- future_priorityはfuture_candidates内でなければならない。
- future_detail_a／bはfuture_priorityに対応する候補定義の選択肢だけを受け付ける。other最優先時はfuture_detail_otherだけを受け付ける。
- submission_tokenのハッシュは同一送信の再試行だけを重複排除する。UID単位の回答数制限には使わない。
- feature_display_orderは26機能ID、future_display_orderは12候補IDを過不足・重複なく含む。
- 1 UIDにつき1回答は保証しない。1 UIDにつき同一キャンペーンの報酬1回だけを保証する。

### 5.5 実装済みの送信外枠とDB列

Webから同一origin APIへ送るPOST bodyは次の2キーだけを持つ。

| キー | 実装値 |
|---|---|
| answers | 5.2の22キーだけを持つ回答本体 |
| submission_token | ブラウザ生成の32-byte base64url値。43文字 |

同一origin APIからEdge Functionへはsurvey_slugを加えた3キーだけを送る。Edge Functionはsubmission_tokenをSHA-256化し、DB RPCへbyteaとして渡す。平文tokenをDBへ保存しない。

DBの物理列:

| テーブル | 列 | UIDとの関係 |
|---|---|---|
| surveys | survey_id、slug、title、description、schema_version、questions、campaign_title_id、opens_at、closes_at、is_active、created_at、updated_at | キャンペーン定義。回答者UIDなし |
| survey_responses | response_id、survey_id、respondent_kind、submission_token_hash、answers、submitted_on | UID列なし。respondent_kindはauthenticated／guestの区分だけ。submitted_onは時刻を持たない日付 |
| survey_reward_claims | survey_id、user_id、awarded_on | UIDを持つ報酬台帳。response_id、answers、submission_token_hashなし |

survey_responsesの一意制約はsurvey_idとsubmission_token_hashの組み合わせであり、user_idではない。survey_reward_claimsの主キーはsurvey_idとuser_idの組み合わせである。両テーブルは同じsurvey_idを持つが、回答個体を示す共通キーは持たない。

回答行のresponse_idは匿名回答側だけの内部IDであり、報酬台帳、セッション、API応答へ保存・公開しない。respondent_kindは個人を示さないが回答者区分を示し、submitted_onと合わせた小さい集団では状況から推測される余地がある。そのため、生回答へのアクセスを限定し、少人数区分を公表しない。これはUIDと回答を直接結合しない契約であり、完全な追跡不能性の保証ではない。

    直近30日間で、PlayNaviを使った日数はどれくらいですか？

補足:

    正確に数えず、おおよそでお答えください。

2. 5〜14日

4. この30日間は使っていないが、以前は使った

6. 覚えていない

1. とても満足
2. やや満足
3. どちらともいえない
4. やや不満

### Q3. 候補提示前の任意記述

質問:

    最近のゲーム生活で、「こうできたら、もっとよいのに」と感じたことはありますか？

補足:

    PlayNavi以外での出来事でもかまいません。短いひとことで大丈夫です。

任意・400文字以内。入力欄は小さく始め、AIやニュース等の候補を例示しない。候補提示後の記述と区別して集計する。

### Q4. 今も役立っている機能

質問:

    これからも使いたい、役に立っていると感じる機能を、最大3つ選んでください。

補足:

    よく使うものだけでなく、必要なときに役立つものも含めてください。

利用経験者に表示。3件を埋める必要はない。26機能は次の7見出しで表示し、各機能へ現行挙動に合う短い用途説明を付ける。

| 見出し | 機能 |
|---|---|
| 最新情報・イベント・お得情報 | game_news: ゲームニュース（ゲームの新情報を読む）、events: イベント情報（ゲーム関連イベントを探す）、subscriptions: サブスクリプション情報（定額サービスの追加・終了を知る）、sales: セール情報（ゲームの値下げを探す） |

## 7. 回答体験

### 7.1 基本操作

- 単一選択と複数選択を見た目でも区別する。
- Q4とQ9の最大件数はノルマではない。
- 複数選択は選択状態を確認してから「次へ」で進み、タップ順を順位にしない。
- 最優先はQ10で選択済み候補から明示する。
- 任意記述とQ5は閉じた状態から始め、任意であることとスキップ方法を隠さない。
- 戻る操作で回答を消さず、いつでも修正できる。
- 同じ内容を複数の自由記述へ再入力させない。
- 下書きは同一タブで復元し、送信完了後に削除する。
- タップ領域は48px相当以上、320px幅と200%文字拡大でも本文を隠さない。
- 固定フッターは最終選択肢を覆わず、横スクロールを発生させない。

### 7.2 自動移動

選択だけで別ページへ自動遷移しない。ポインタ操作で同じページ内の次の単一設問を表示範囲へ移す場合は、選択結果が見え、すぐ修正でき、キーボードや支援技術で予期しないフォーカス移動が起きないことを条件とする。Q4、Q9、任意入力では自動移動せず、明示的な「次へ」を使う。

### 7.3 表示順

- Q4の26機能とQ9の12候補は回答ごとに順序をランダム化し、実際の順序を`feature_display_order`／`future_display_order`へ保存して同一下書きの再表示時に固定する。
- 頻度、満足度、回数等の順序尺度は並べ替えない。
- その他、特にない、判断できないは末尾の固定位置にする。
- 26機能はカテゴリ内の理解しやすいまとまりを壊して無秩序に並べ替えない。
- 表示順はUIDから生成しない。

### 7.4 分岐変更

- Q9からfuture_priorityを外した場合だけQ10の選び直しを求め、他の無順位候補は保持する。
- Q10変更時は旧候補のQ11回答を送信対象から除外する。
- Q6またはQ10変更時はQ12の比較対象と回答を無効化する。
- Q1変更時は新経路で非表示になった回答を送信対象から除外する。
- 非表示値を再表示時に復元するかは下書き内に限る。送信payloadには現在の有効分岐だけを含める。

## 8. 匿名回答と報酬

### 8.1 保存境界

    回答受付
    ├─ 匿名回答保存
    │  ├─ schema v3 payload
    │  ├─ UIDなし
    │  └─ UIDへ戻る外部キー・共通response IDなし
    └─ アカウント回答時だけ報酬処理

       ├─ 称号付与状態
       └─ 回答ID・回答本文なし

アカウント回答では、認証・セッションの正当性確認にUIDを一時的に処理する。有効期限付きのhandoff code／Web sessionは認証を成立させる間だけUIDを保持するが、回答ID、回答本文、submission token hashを持たず、回答へ結合できない。これらの一時セッションは回答送信直後ではなく有効期限で失効し得るため、報酬台帳以外からUIDが即時消去されるとは説明しない。認証後のUIDは報酬資格と既付与判定にだけ使い、同じUIDからの再回答拒否、回答件数制限、回答保存、集計には使わない。長期保存する回答・報酬のキャンペーン業務データでは報酬台帳だけがUIDを持つ。回答保存領域と報酬台帳には、互いを直接結合できるresponse_id、外部キー、submission_token_hashを共通で持たせない。

アカウント回答では、匿名回答のinsert、報酬台帳のupsert、称号付与を一つのDB transactionで行い、途中失敗時はすべてrollbackする。共通IDを保存しなくても原子性は維持する。その上で次を独立して保証する。

- 有効な回答本体の保存に成功した場合だけ報酬処理へ進む。
- 報酬台帳はsurvey_idとUIDの組み合わせを一意にし、同じキャンペーン報酬を二重付与しない。
- 回答選択、賛否、自由記述の有無は付与条件に使わない。
- 既に報酬取得済みのUIDから再度有効回答が送られた場合、回答は匿名で受け付け得るが報酬は追加しない。
- UIDを回答件数制限へ利用しないため、1 UIDにつき1回答は保証しない。
- ネットワーク再試行はUIDと無関係なsubmission_tokenのハッシュで同一送信だけを重複排除する。
- ゲストはUIDと報酬台帳を使わない。

### 8.2 データ最小化

- URL、アプリログ、一般分析ログ、エラー監視へUID、回答本文、認証情報を送らない。
- 回答保存APIのログへpayload本文を残さない。
- IPアドレスやUser-Agentを回答行へ保存しない。
- 自由記述の閲覧権限を限定し、集計APIから返さない。
- 集計APIはUID、報酬台帳、生回答、自由記述を返さない。
- 回答と報酬台帳を別テーブルに分け、回答集計経路から報酬台帳を参照しない。いずれも公開ロールへ直接公開しない。
- 回答行のrespondent_kindとsubmitted_onは個人識別子ではないが、少数回答や外部ログとの状況的な突合せ可能性まで否定しない。
- 保存期間、削除時期、閲覧担当、問い合わせ窓口を公開前に確定する。

### 8.3 利用者への説明

    回答データの利用について

    回答は、PlayNaviの機能改善と開発優先度の検討に利用します。
    回答内容はUIDに紐づけず、匿名で保存・集計します。
    アカウントで回答する場合、UIDは回答完了の称号を付与するためだけに使用します。
    回答本文を他のユーザーへ公開することはありません。
    自由記述には、氏名、メールアドレス、SNSアカウント、認証情報を書かないでください。
    匿名保存のため、送信後はUIDから個別回答を特定して変更・削除することはできません。

同意方法、プライバシーポリシーへのリンク、匿名回答の保持・一括削除方針は公開前に承認する。

## 9. 集計仕様

### 9.1 主指標

| 対象 | 集計 | 解釈上の制限 |
|---|---|---|
| Q1 | 利用状況別の人数と割合 | 旧尺度と直接比較しない |
| Q2 | 利用状況別の満足度分布 | 休眠者の回顧評価を現在利用者と分ける |
| Q3 | 非誘導の期待・課題テーマと件数 | 記述者だけ。空欄をニーズなしとしない |
| Q4 | 機能別選択人数／Q4対象者数 | 顕在価値の最大3件。順位、利用率、重要度、不要率ではない |
| Q5 | 機能×未利用理由の件数 | 任意回答。全体の認知率、未利用率にしない |
| Q6 | 最重要問題の人数／Q6対象者数 | 全問題の経験率ではない |
| Q6-L | 休眠理由の分布 | Q6と混ぜない |
| Q7 | 問題別の自己申告行動結果 | 最重要問題を選んだ人だけ |
| Q8 | 方向性1位の人数／Q8回答者数 | 大方向の比較用 |
| Q9 | 候補別選択人数／Q9回答者数 | 順位なし。noneとunknownも別集計 |
| Q10 | 最優先人数／Q9回答者数 | inheritedとexplicitを識別可能にする |
| Q11 | 最優先者内の具体希望・条件 | 候補間で条件付き比率を直接比較しない |
| Q12 | 同じ問題×候補ペア内の内訳 | 異なるペアを資源配分率として合算しない |

Q9へ3点、2点、1点の加重スコアを作らない。

### 9.2 区分

- 現在利用、休眠、未利用、不明。
- authenticated、guest。サーバーが回答行へ設定するrespondent_kindだけで区分し、UIDと結合しない。
- 募集経路は信頼できる取得経路が未実装なのでschema v3では保存・集計しない。将来追加する場合は新しい契約として承認する。
- 小さい区分では割合だけを強調せず、人数と分母を併記する。

### 9.3 判断原則

- ニュース、他人の投稿、自分の投稿、クリエイター紹介、独自企画の票を足し、候補数の違いを無視して大領域の支持率にしない。
- Q8は方向性、Q9・Q10は候補選別、Q11は仕様の絞り込みとして使い分ける。
- 同点や数票差を細かな順位として断定しない。
- 支持人数、既存の困りごと、行動、必要条件、開発・運用負荷、依存関係を並べて判断する。
- F3支持を外部自動連携への支持や手動MVPへの支持と同一視しない。
- F4と称号機能の評価では、回答報酬が称号であることによる回答者構成の偏りに留意する。
- Q4非選択やQ5の少数意見だけで機能を削除しない。
- クリエイターの参加意思や送客価値は、クリエイター本人への別調査で確認する。

### 9.4 除外

自動的に含めないもの:

- 送信前の下書きと離脱回答
- サーバー検証を通らない回答
- 同じsubmission_token_hashによる通信再試行
- STG、QA専用slugの回答

自動除外しないもの:

- すべて同じ種類の選択をした回答
- 短時間で完了した回答
- ゲスト回答
- 同一UIDからの可能性がある複数回答。回答本体はUIDと結び付かないため判定しない

品質除外を追加する場合は基準を公開前に固定し、除外前後を併記する。

## 11. schema v2からの移行

schema v2は7カテゴリ、26機能の全必須優先度、カテゴリTop、詳細重要度・満足度、将来7候補の順位を固定している。schema v3はラベル変更では実現できない。

変更対象:

1. キャンペーン定義と設問ID
2. Web画面、状態管理、下書き、分岐、payload生成
3. WebとEdge Functionのvalidator
4. DBの匿名回答保存、報酬台帳、称号付与処理
5. 集計APIまたはRPC
6. schema v2とv3、accountとguest、全分岐のテスト
7. Runbook、STG seed、production one-shot SQL

維持する契約:

- 4.2.2以降のアプリ認証引継ぎ
- 4.2.1以前と共通Web URLのGoogle／Appleログイン
- ゲスト導線
- 任意回答と評価内容に依存しない称号
- 下書き復元と送信後削除
- 64KiB上限
- 集計APIから生回答と自由記述を返さない
- STGとproductionのslug分離

意図的に変更する契約:

- 26機能の全件採点を、役立つ機能最大3件へ変更
- カテゴリ順位と全詳細評価を廃止
- 将来関心ゲートを廃止
- 将来候補を7件から12件へ変更
- 順位付きTop3を無順位最大3件＋最優先1件へ変更
- 利用経験による分岐を追加
- UIDを回答保存・回答重複防止から除外し、報酬だけへ限定
- account回答でも1 UIDにつき1回答を保証しない

既存STG回答を受け付けたslugを意味変更で上書きしない。新STG slugへv3定義を作り、旧回答と集計を隔離する。

### 11.2 実装済み物理契約の照合結果

- Webの`VOICE_V3_ANSWER_KEYS`、Web validator、Web API proxy、DB validatorは5.2の22キーで一致する。
- Web fixtureと新STG seedは、questions.kind、7カテゴリ、26機能ID・説明、12候補、Q11全12候補のa／b選択肢までJSON完全一致する。
- F10は`bulk_edit_logs`、`bulk_edit_wishlist`、`long_text`、`compare_research`、`profile_posts`を分け、PC固有の一覧・一括編集、長文入力、比較を測る。
- `respondent_kind`、`submission_token`、slug、schema_versionは回答本体22キーの外側にあり、UIDは回答payload、回答行、集計に存在しない。
- DB集計はQ5、Q7、Q12を条件付きの組み合わせ別に返し、異なる母数を単純合算しないための値を保持する。
- schema v1／v2のread、validator、保存、集計経路は残し、schema v3のslugと回答を混ぜない。
- Webは`npm test` 66件、MJS構文検査、iPhone 390×844／Android 412×915の実Chrome検査を通過した。
- DBはDocker上でforward verify、fixture、v3 STG migrationの集計assert、copy guardを通過した。Denoで定義した7件は実行環境未導入のため、STG適用前の残検証とする。

最初のproduction回答を受け付けた時点で、次を凍結する。

- slug、schema version、設問ID
- 設問文、選択肢の意味と順序規則
- 必須、任意、分岐、文字数、件数
- 候補と機能IDの対応
- 匿名保存と報酬分離の契約
- 集計定義、分母、除外条件

意味が変わる誤字修正、選択肢追加、カテゴリ移動、分岐変更は同じproduction slugで行わない。新schemaまたは新slugを作り集計を分ける。

- 新STG slugだけを使用する
- アプリ認証引継ぎ、Google、Apple、guestを確認する
- 現在利用（days_1_4等）、休眠（inactive_30d）、未利用（never_used）、不明（unknown）を少なくとも1件ずつ送信する
- anonymous responseにUIDがないことをDBで確認する
- survey_reward_claimsと称号付与がauthenticatedだけに1回記録されることを確認する
- 2回目回答をUIDで拒否せず、称号を二重付与しないことを確認する
- 集計値を投入した期待値と照合する
- schema v2の既存回答と集計が変わらないことを確認する

## 16. 設計根拠

- 全26機能の反復採点ではなく、守る価値、未利用理由、最大問題を分けて聞き、回答負荷を下げる。
- 候補提示前の任意記述で、作り手の候補による誘導を減らす。
- 大きな方向性、候補選択、最優先、具体条件を別設問にし、異なる粒度の票を混ぜない。
- 複数選択は順位なし、最優先だけ明示し、下位へ無理に差を付けさせない。
- PC版は提供端末名ではなく、PC固有の一覧性、編集効率、長文入力、比較という利用価値を測る。
- 回答とUIDを分離し、回答内容を報酬や既存行動履歴へ結び付けない。
- 任意記述と回答内容を報酬から切り離し、インセンティブによる回答誘導を抑える。
